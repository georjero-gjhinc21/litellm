# LiteLLM Free-Model Gateway

Self-hosted [LiteLLM](https://docs.litellm.ai) proxy (podman) exposing **free** LLM models via OpenCode Zen, with a complexity-based auto-router.

## What's here

- `config.yaml` — **auto-generated**. `model_list` of free Zen models + `smart-router` (SIMPLE / MEDIUM / COMPLEX / REASONING tiers). Do not edit manually.
- `docker-compose.yml` — proxy + Postgres, reads secrets from `.env`.
- `.env.example` — reference only now; `.env` itself is generated by `scripts/load_secrets_from_bitwarden.sh` (gitignored, shredded after each deploy) rather than hand-edited.
- `scripts/load_secrets_from_bitwarden.sh` — fetches `LITELLM_MASTER_KEY`, `LITELLM_SALT_KEY`, `UI_USERNAME`/`UI_PASSWORD` and `OPENCODE_API_KEY` from Bitwarden and writes `.env`. Requires `bw` + `jq` on PATH and `BW_CLIENTID`/`BW_CLIENTSECRET`/`BW_PASSWORD` set in the calling shell's environment (never written to disk). Vault items needed: `LiteLLM - Master Key`, `LiteLLM - Salt Key`, `LiteLLM - UI Login` (username + password), `LiteLLM - OpenCode Zen Key` — same vault/pattern as [`../gjh-blog-agent/BITWARDEN_SETUP.md`](https://github.com/georjero-gjhinc21/gjh-blog-agent/blob/main/BITWARDEN_SETUP.md).
- `scripts/update_free_models.py` — discovers free models (models.dev + Zen `/models`), live-probes each, regenerates `config.yaml`.
- `scripts/pull_deploy.sh` — cron entrypoint: pulls latest config and restarts the proxy if changed.
- `last_report.json` — last discovery run (candidates / live / dead).
- `requirements.txt` — Python dependencies (includes `bitwarden-sdk` for optional Bitwarden Secrets Manager integration).

## Bitwarden Secrets Manager Integration (Optional)

The updater script can fetch `OPENCODE_API_KEY` from Bitwarden Secrets Manager instead of `.env`. To use:

1. Create a **machine account** in Bitwarden Secrets Manager with read access to a project
2. Add a secret named `OPENCODE_API_KEY` (or custom name) with your OpenCode Zen API key
3. Set these environment variables (in `.env` or GitHub Actions secrets):
   - `BITWARDEN_ORG_ID` — your organization ID
   - `BITWARDEN_ACCESS_TOKEN` — machine account access token
   - `BITWARDEN_SECRET_KEY` — secret key name (default: `OPENCODE_API_KEY`)

The script checks sources in order: `OPENCODE_API_KEY` env var → Bitwarden → `.env` file.

## Daily model refresh (GitHub Actions + local deploy)

Split so it costs $0 and needs no always-on compute from Actions:

1. **GitHub Actions** (`.github/workflows/update-free-models.yml`, cron 03:30 UTC + manual dispatch) runs `scripts/update_free_models.py` with the `OPENCODE_API_KEY` secret (and optional Bitwarden secrets), regenerates `config.yaml`, self-commits and pushes (heartbeat commit keeps the 60-day inactivity timer from disabling the schedule).
2. **Local cron** (`*/15 * * * *`) runs `scripts/pull_deploy.sh` — pulls `main` and restarts the proxy container only when `config.yaml` changed.

The proxy itself stays on this host (GitHub runners are ephemeral and can't host it).

## Usage

```bash
# proxy up:
podman-compose -p gvincent -f docker-compose.yml up -d
# chat (direct or via smart-router):
curl http://localhost:4000/v1/chat/completions \
  -H "Authorization: Bearer sk-1234" \
  -d '{"model":"smart-router","messages":[{"role":"user","content":"hi"}]}'
```

Cron (installed): `*/15 * * * * /home/gvincent/litellm/scripts/pull_deploy.sh` — pulls `main`, restarts the proxy if `config.yaml` changed. Model discovery runs in GitHub Actions (03:30 UTC daily).

### A note on the Bitwarden bootstrap

`load_secrets_from_bitwarden.sh` needs `BW_CLIENTID`/`BW_CLIENTSECRET`/`BW_PASSWORD` in its environment to unlock the vault — that one bootstrap credential can't itself come from Bitwarden. Chosen approach here: export those three manually in the host's own shell session before a restart happens, rather than writing them to a file. The tradeoff: cron runs non-interactively and won't see vars from a login shell, so `pull_deploy.sh`/`run_daily.sh` only refresh `.env` from Bitwarden when they find those three vars already in their environment; otherwise they fall back to whatever `.env` is already on disk (if any) and just restart the container with it. In practice this means running `pull_deploy.sh` or `run_daily.sh` by hand (with the three vars exported) after any Bitwarden secret rotation, so a fresh `.env` gets written once and the unattended cron restarts keep reusing it until the next manual refresh.
